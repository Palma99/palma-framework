# API DI: registrazione manuale e wiring automatico

Il generatore implementa `pfw.Build`, `BuildWithCleanup`, `Constructors`, `Discover`, `Exclude`,
`Implementation`, `Bind` e `Module`.
L'API è iniziale e potrà evolvere. Il module path è
`github.com/palma99/palma-framework`; il package Go, la CLI e i marker usano `pfw`.

L'utente può registrare i costruttori manualmente o far scoprire quelli annotati
nei package selezionati. Il frontend produce lo stesso grafo tipizzato in
entrambi i casi; il framework risolve e genera il wiring.

## Provare il generatore

Dal repository:

```sh
go run ./cmd/pfw generate ./examples/httpapi/internal/bootstrap
go run ./cmd/pfw generate -check ./examples/httpapi/internal/bootstrap
go test ./...
go run ./examples/httpapi/cmd/api
```

L'API di esempio espone `GET http://localhost:8080/users`. Usa un repository
in memoria, costruttori in package diversi e il router Echo v5.
Il server usa il lifecycle del framework e l'adapter `transport/httpserver`.
Gli adapter dedicati per altre librerie HTTP sono i passi successivi.

Si può anche installare la CLI con `go install ./cmd/pfw`, rendendo disponibile
`pfw generate` se la directory dei binari Go è nel `PATH`.
La direttiva `go:generate` nell'esempio permette `go generate ./examples/httpapi/internal/bootstrap`.
La compilazione non esegue automaticamente la generazione.

## Costruttori normali

I servizi non importano Palma. Un costruttore dichiara le dipendenze nei suoi
parametri e restituisce un servizio, eventualmente con un errore:

```go
func OpenRepository(cfg Config) (*SQLRepository, error)
func NewUserService(repo UserRepository) *UserService
func NewApplication(users *UserService) *Application
```

Le firme qui sono illustrative; i corpi appartengono all'applicazione.
Non è richiesto un prefisso come `New`, né una directory dedicata.

## Dichiarazione del composition root

L'utente scrive una funzione con il nome, i parametri e il tipo risultato che
desidera. Il corpo dichiara la composizione, che il generatore sostituirà con
chiamate Go concrete:

```go
//go:build pfw_inject

package bootstrap

import pfw "github.com/palma99/palma-framework"

func Initialize(cfg Config) (*Application, error) {
    return pfw.Build[*Application](
        pfw.Constructors(OpenRepository, NewUserService, NewApplication),
        pfw.Implementation[UserRepository, *SQLRepository](),
    )
}
```

Nell'esempio i tipi e i costruttori sono accessibili nel package `bootstrap`.
Possono anche provenire da altri package, usando normali import e simboli
qualificati. `bootstrap` e `Initialize` sono nomi di esempio, senza significato
speciale per il framework.

Il build tag separa le dichiarazioni dal programma finale. Il generatore
caricherà i template con `pfw_inject`; il file emesso avrà il tag inverso
`!pfw_inject`. Non è richiesto un nome particolare per il file del template.
Il tag è un meccanismo di compilazione, non una convenzione architetturale.

### Operazioni di registrazione

| Operazione | Significato |
| --- | --- |
| `Constructors(f, g, ...)` | Registra i costruttori indicati tramite simboli Go. |
| `Discover(patterns...)` | Registra le funzioni annotate `//pfw:coconut` nei package selezionati. |
| `Exclude(f, g, ...)` | Esclude funzioni dalla discovery; mantiene le registrazioni manuali. |
| `AutoBind()` | Abilita il binding automatico nel modulo che lo contiene. |
| `Implementation[Interface, Concrete]()` | Seleziona esplicitamente l'implementazione dell'interfaccia. |
| `Bind[Interface, Concrete]()` | Alias di `Implementation`, con lo stesso ordine dei tipi. |
| `Module(...)` | Raggruppa registrazioni riutilizzabili, anche annidate. |
| `Build[T](...)` | Dichiara il tipo radice da costruire per quella funzione. |
| `BuildWithCleanup[T](...)` | Costruisce la radice e restituisce il cleanup delle risorse. |

`Build[T]` ha firma di ritorno `(T, error)` nel primo incremento.
Le operazioni descrivono il grafo per il generatore: non costruiscono un
container e non vengono eseguite per risolvere dipendenze a runtime.

`Implementation[Interface, Concrete]()` e `Bind[Interface, Concrete]()` sono
equivalenti: producono lo stesso binding, gli stessi controlli e lo stesso
codice generato. Si può scegliere il nome più naturale; registrarli entrambi
per la stessa interfaccia resta una registrazione duplicata.

I parametri della funzione di inizializzazione diventano input del grafo in
base al loro tipo dichiarato. Nell'esempio `cfg` soddisfa la dipendenza `Config`
di `OpenRepository`. Due input dello stesso tipo, oppure un input e un provider
per lo stesso tipo, sono ambigui e devono produrre un errore di generazione.
Qualificatori per distinguere istanze dello stesso tipo sono rimandati.

## Codice generato

Per il template sopra, il risultato atteso è equivalente a:

```go
// Code generated by pfw. DO NOT EDIT.
//go:build !pfw_inject

package bootstrap

import "fmt"

func Initialize(cfg Config) (*Application, error) {
    repository, err := OpenRepository(cfg)
    if err != nil {
        return nil, fmt.Errorf("pfw: OpenRepository: %w", err)
    }
    users := NewUserService(repository)
    application := NewApplication(users)
    return application, nil
}
```

Il binding non richiede un lookup: il codice passa il valore concreto dove Go
accetta l'interfaccia. La scelta viene verificata tramite i tipi prima
dell'emissione. Errori dei costruttori vengono propagati mantenendo la causa.

Per radici non pointer il percorso di errore deve restituire il valore zero
del tipo radice. Ogni provider raggiungibile viene chiamato una sola volta
per invocazione di `Initialize`; due invocazioni creano due grafi distinti.
Un input fornito dal chiamante conserva invece l'identità del valore passato.

## Discovery con coconut

Il marker si scrive nel commento di documentazione sopra la funzione:

```go
//pfw:coconut
func NewService(repo Repository) *Service {
    return &Service{repository: repo}
}
```

Non sono richiesti nomi o cartelle speciali. Il commento rende la funzione
disponibile soltanto se il suo package è selezionato tramite `Discover`:

```go
var Services = pfw.Module(
    pfw.Discover("../user/..."),
    pfw.Constructors(NewExternalClient),
    pfw.Implementation[Repository, *Store](),
)
```

I pattern sono costanti stringa Go: possono essere import path oppure percorsi
relativi alla directory del package che contiene il template. Questo riferimento
resta lo stesso anche quando la CLI viene eseguita dalla root del repository.
`...` seleziona i sotto-package. Un pattern senza package produce un errore.
La discovery rispetta il contesto di build Go corrente e non analizza file di
test o file esclusi dai build tag. Non esegue funzioni o inizializzazioni utente.

Sono supportate tutte le firme dei costruttori, compresi quelli con cleanup.
Le funzioni non annotate rimangono registrabili con `Constructors`. Metodi,
funzioni generiche o firme non supportate annotate producono una diagnostica.
Una funzione privata è utilizzabile solo se l'initializer è nel suo package;
altrimenti va esportata. Restano validi i vincoli degli import Go e di `internal`.

Una stessa funzione viene registrata una sola volta, anche se selezionata da
pattern sovrapposti o dichiarata anche manualmente. Funzioni diverse che
forniscono lo stesso tipo rimangono ambigue. L'autobinding delle interfacce
è disabilitato di default e si abilita esplicitamente per modulo.

### Binding automatico delle interfacce

```go
var Users = pfw.Module(
    pfw.Discover("../user/..."),
    pfw.AutoBind(),
)
```

`AutoBind()` è ammesso soltanto dentro `Module`. Vale per i suoi provider,
inclusi i moduli annidati; abilitarlo in un modulo figlio non lo abilita nel
padre o nei moduli fratelli. La posizione del marker fra gli argomenti non conta.

Per ogni interfaccia richiesta da una dipendenza o dalla radice:

1. Se esiste `Implementation` o `Bind`, si usa il tipo concreto specificato.
2. Se un input o costruttore fornisce già esattamente l'interfaccia, si usa quel valore.
3. Se il costruttore appartiene a un modulo con `AutoBind`, si cercano candidati
   concreti soltanto fra i provider di quel modulo e dei suoi discendenti.
   Senza opt-in si richiede un binding manuale.
4. Un solo candidato viene selezionato; più candidati producono un errore con
   l'elenco e la richiesta di un binding manuale; nessuno produce una dipendenza mancante.

Il controllo usa il method set Go: `T` e `*T` non sono intercambiabili. Non si
analizzano tutti i tipi dichiarati nel progetto: contano soltanto i valori che
il grafo può fornire. Gli esclusi dalla discovery non sono candidati, a meno
che siano registrati manualmente. La regola vale sia per registrazione manuale
sia per discovery, anche per risorse con cleanup. I servizi condividono la stessa
istanza scelta, anche quando richiesta attraverso più interfacce.

Due moduli con `AutoBind` possono scegliere tipi diversi per la stessa
interfaccia: il piano conserva le scelte per costruttore. I provider esterni al
modulo non introducono candidati impliciti. Un costruttore condiviso fra più
moduli mantiene una sola istanza; se appartiene a più scope automatici, i loro
candidati vengono riuniti e le ambiguità richiedono un binding esplicito.
Per una radice di tipo interfaccia si considerano i provider dei moduli che
hanno abilitato `AutoBind`; più candidati richiedono un binding manuale.
Gli input esterni concreti non appartengono ai moduli: per convertirli in
interfacce serve `Bind`/`Implementation`, oppure un parametro già tipizzato
come interfaccia. I binding espliciti valgono per l'intera composizione e
mantengono sempre la precedenza.

La selezione è statica e compare nel piano generato. Non esistono lookup runtime
o priorità basate sull'ordine di registrazione. Un binding manuale non costruisce
automaticamente un provider mancante: il tipo selezionato deve essere disponibile.

Per sostituire un costruttore scoperto:

```go
pfw.Module(
    pfw.Discover("../storage/..."),
    pfw.Exclude(storage.Open),
    pfw.Constructors(OpenTestStorage),
)
```

L'esclusione riguarda soltanto la discovery ed è indipendente dall'ordine.
Una registrazione manuale esplicita dello stesso costruttore resta disponibile.
Le annotazioni non aggiungono dipendenze runtime da Palma ai servizi.

## Risorse e cleanup

Tutte queste firme sono supportate; soltanto le risorse richiedono il cleanup:

```go
func NewService(repo Repository) *Service
func NewClient(cfg Config) (*Client, error)
func OpenDatabase(cfg Config) (*Database, func() error, error)
```

Se il grafo raggiungibile contiene un costruttore con cleanup, usare il marker
`BuildWithCleanup` e dichiarare tre risultati nella funzione di inizializzazione:

```go
func Initialize(cfg Config) (*Application, func() error, error) {
    return pfw.BuildWithCleanup[*Application](
        pfw.Constructors(OpenDatabase, NewService, NewApplication),
    )
}
```

I costruttori semplici mantengono le loro firme; non devono aggiungere risultati.
`Build` continua a restituire `(T, error)` e il generatore segnala un errore se
viene usato per un grafo che richiede cleanup. Un provider con cleanup registrato
ma non raggiungibile dalla radice non viene costruito e non richiede il marker.

### Contratto di ownership

- Alla riuscita dell'inizializzazione, il chiamante riceve un cleanup non nil.
  Deve invocarlo dopo che l'applicazione ha terminato di usare i servizi.
- Il cleanup chiude le risorse in ordine inverso alla costruzione, una sola volta,
  anche in presenza di chiamate concorrenti. Le chiamate successive restituiscono
  l'errore già calcolato.
- Un errore di cleanup non impedisce l'esecuzione degli altri callback. Gli errori
  vengono aggregati e restano verificabili con `errors.Is` e `errors.As`.
- Se un costruttore fallisce, il generatore esegue automaticamente il cleanup e
  restituisce il valore zero della radice, cleanup nil e l'errore di costruzione
  aggregato agli eventuali errori di cleanup.
- Un callback non nil restituito da un costruttore trasferisce al wiring la
  responsabilità di eseguirlo **anche se lo stesso costruttore restituisce errore**.
  Serve anche a rilasciare risorse parzialmente inizializzate. Se il costruttore
  ha già ripulito la risorsa internamente, deve restituire cleanup nil.
- I callback nil vengono ignorati. `BuildWithCleanup` senza risorse restituisce
  un cleanup che non esegue operazioni e restituisce nil.
- Gli input esterni rimangono di proprietà del chiamante: il generatore non
  ne deduce o invoca metodi di chiusura.

Per gestire anche gli errori di chiusura, un chiamante può usare `errors.Join`:

```go
func run(cfg Config) (err error) {
    app, cleanup, err := Initialize(cfg)
    if err != nil {
        return err
    }
    defer func() { err = errors.Join(err, cleanup()) }()
    return app.Run()
}
```

Il file che usa questo esempio importa `errors` dalla standard library.
`examples/cleanup` è un esempio eseguibile con una risorsa simulata, senza DB:

```sh
go run ./cmd/pfw generate ./examples/cleanup
go run ./examples/cleanup
```

## Moduli

Le registrazioni possono essere raggruppate, ad esempio nel template:

```go
var Storage = pfw.Module(
    pfw.Constructors(OpenRepository),
    pfw.Implementation[UserRepository, *SQLRepository](),
)

func Initialize(cfg Config) (*Application, error) {
    return pfw.Build[*Application](
        Storage,
        pfw.Constructors(NewUserService, NewApplication),
    )
}
```

Il nome del modulo è libero; la sua posizione non determina la posizione dei
servizi. I moduli nello stesso package, anche annidati, sono supportati.
I moduli fra package non sono ancora supportati; i costruttori fra package
lo sono. Tutti i manifest che usano i marker devono essere esclusi dal programma
finale tramite il tag di generazione. I moduli non possono essere riassegnati
o utilizzati fuori dalle dichiarazioni statiche di registrazione.

Un modulo è una dichiarazione statica. Il generatore legge registrazioni e
riferimenti; non esegue funzioni utente per scoprire il grafo.

## Perimetro del primo generatore

- Costruttori dichiarati come funzioni non generiche: `func(...) T`,
  `func(...) (T, error)` e `func(...) (T, func() error, error)`.
- Un solo servizio restituito per costruttore, con eventuali cleanup ed `error`.
- Dipendenze per identità di tipo, interfacce con binding esplicito o automatico
  opzionale per modulo in presenza di un candidato unico.
- Parametri della funzione di inizializzazione come input esterni.
- Funzione di inizializzazione non generica con risultato `(T, error)` oppure
  `(T, func() error, error)` per `BuildWithCleanup`.
- Registrazioni statiche tramite le operazioni sopra.
- Output deterministico, formattato e nel package della funzione template;
  nome del file configurabile con `-output` (default `pfw_gen.go`).
- Diagnostica con posizione del template e controllo dei tipi prima della scrittura.
- `-check` per verificare file mancanti o non aggiornati, senza modificarli.
- Protezione dei file esistenti che non sono stati generati da `pfw`.

Firme variadiche, metodi come provider, closure, registrazioni dinamiche,
qualificatori e moduli fra package non sono ancora supportati.
Le forme non supportate devono essere rifiutate con una diagnostica, senza
interpretazioni implicite. Il callback di cleanup può essere affidato al
[lifecycle applicativo](lifecycle.md), che lo esegue dopo l'arresto dei componenti.

Il generatore usa un template nel package del composition root: per cambiare
package di destinazione si colloca il template in quel package. Il generatore
non muove dichiarazioni e non aggira le regole di visibilità Go.

Per questo primo incremento i template richiedono esattamente il tag
`pfw_inject`: condizioni composte con ulteriori build tag non sono supportate.
Target e moduli vengono caricati usando il contesto Go corrente.
Non compilare o avviare applicazioni con il tag `pfw_inject`: `Build` è un
marker e, se eseguito, fallisce esplicitamente.

## Editor e navigazione nei template

I template sono esclusi dalla build normale. Per abilitare diagnostica,
completamento e navigazione in `gopls`, configurare il tag soltanto nel
language server. Per VS Code e gli editor compatibili, in `.vscode/settings.json`:

```json
{
  "gopls": {
    "buildFlags": ["-tags=pfw_inject"]
  }
}
```

Il repository include questa configurazione. Dopo una modifica alle impostazioni,
riavviare il language server Go se l'editor non ricarica automaticamente.
Nel contesto dell'editor vengono analizzati i template al posto di `pfw_gen.go`,
che ha il tag inverso. Build e test dell'applicazione continuano a utilizzare
il codice generato. Non impostare il tag in `GOFLAGS` globali o nei flag dei
test: l'applicazione compilata con i template eseguirebbe il marker `Build`.

Riferimento: [configurazione buildFlags di gopls](https://go.dev/gopls/settings#buildflags-string).

## Verifiche

L'esempio HTTP utilizza un repository in memoria, un'interfaccia applicativa
e provider in package diversi senza dipendenze del dominio da Palma.

I test del generatore compilano ed eseguono l'output, verificano riuso delle
dipendenze, propagazione degli errori, determinismo e diagnostica dei grafi non
validi. L'endpoint HTTP viene verificato tramite `httptest`. Successivamente
si collegherà una seconda libreria HTTP allo stesso servizio applicativo.
